# 并行：为什么能开几十路子代理，怎么开

这套方法最关键的工程决策是：**把整本书切成互不依赖的小任务，一个任务交给一个独立上下文。**
不是"让一个大模型读完整本书"，是"几十个子代理各读一片，最后机械合并"。

## 一、为什么能并行

| 条件 | 这套流程怎么满足 |
|---|---|
| 任务之间没有依赖 | 一层摘要：一片一个任务，读完写自己的文件，谁也不看谁 |
| 输入输出都落盘 | 输入是 `chunks/chunk_NN.txt`，输出是 `notes/chunk_NN.md`，路径唯一 |
| 失败可隔离 | 第 37 片失败不影响其他 77 片，重跑只补 37 |
| 可断点续跑 | 已存在的输出直接跳过，中断了重跑同一条命令 |
| 上下文不共享也不需要 | 每一片的信息量本来就装得下一次调用，不需要全局视野 |

**反面例子**：把 400 万字塞进一个上下文做"全书通读"。那是必崩的，不是模型不行，是任务设计错了。

## 二、并行粒度

| 阶段 | 任务数 | 单任务输入 | 实测并发 |
|---|---|---|---|
| `02_run_notes.py` 一层摘要 | = 片数（25 / 78 / 上百） | 1 片 ≈5.2 万字 ≈31k–60k token | **25–78 路** |
| `05_run_volumes.py` 二层卷纪要 | = 卷数（26–78） | 几份摘要 6–9k 字 ≈4–6k token | **30–35 路** |
| `05_run_volumes.py --meta` 元章节 | 6 个 | 压缩材料 ≤6 万字 | 6 路 |
| `06/07/09/10/11` | 单进程 | — | 本地跑，不并发 |

实测记录（两个真实项目）：

```
《奶妈》   114 万字 → 26 片   → 25 路并发摘要，一次跑完
《无职转生》444 万字 → 78 片  → 76 路并发摘要（PAR=50 排队跑完）
                               → 35 路二层卷纪要 + 9 路外传分组
```

**上一层和下一层之间不需要串行等待到"全部完成"**——但建议跑完再合并，
因为合并脚本要做覆盖率校验，缺片会提醒你。

## 三、三种跑法（选一个）

### A. 子代理（推荐；每个子代理一个独立上下文）

适合已经有 agent CLI 的场景。要点是**一个子代理只干一片**，别让它"顺便看看全局"。

```bash
# 任务清单：一行一片，交给并发调度器
ls chunks/chunk_*.txt | xargs -P 50 -I{} bash -c '
  n=$(basename {} .txt)
  [ -s notes/$n.md ] && exit 0                      # 已完成就跳过
  my-agent --no-session --mode text \
           --tools read,write \                     # 只给读写，别给它联网
           "分页读完整文件 {}（读到片尾，不要跳读），按 config/prompts/stage1_note.txt
            的字段格式写结构化中文摘要到 notes/$n.md，全中文 900-1500 字，
            文中「原文文风样本」必须逐字摘自原文。完成后回复 DONE"
'
# 占位符说明：{prompt_file} / {out_file} / {chunk_file} 由 lib/llm.py 的 command 后端替换
```

对应到仓库里的配置就是 `backend: command`：

```jsonc
"llm": {
  "backend": "command",
  "command": "my-agent -p --no-session --tools read,write < {prompt_file} > {out_file}",
  "concurrency": 50,
  "timeout": 1800,
  "retries": 3
}
```

子代理模式的三个好处：
1. **上下文天然隔离** —— 第 12 片的内容永远不会污染第 13 片的摘要。
2. **可以给它工具** —— 让它自己分页读文件（长片模型单次读会被截断，子代理能 `offset` 续读）。
3. **失败可见** —— 每个子代理一个日志文件，哪片挂了看日志就懂。

### B. API 批处理（本仓库默认）

```bash
python scripts/02_run_notes.py --par 32
```

`lib/llm.py` 用线程池打 `/chat/completions`，失败的自动退避重试，
每片一份日志落在 `logs/notes/`。片内容直接内联进提示词，不需要模型自己读文件。

### C. 人工多开窗口（没有编程条件时的退路）

一片一个对话，把 `config/prompts/stage1_note.txt` 里的正文换成该片内容，复制粘贴。
慢，但机制完全一样：**任务独立、输出落盘、格式统一**。

## 四、并发数是拍脑袋定的吗

不是，按两件事定：

1. **额度**：云 API 的 RPM/TPM、本地推理的显存/并发槽位。
2. **单任务时长**：一片 5 万字，输出 1.5k 字，多数模型 30–120 秒。

排空时间 ≈ `任务数 ÷ 并发 × 单任务耗时`。78 片、50 路并发、单片 1 分钟 ≈ 2 分钟排空。

并发太高会撞限流，`lib/llm.py` 里的 `retries` + 指数退避会兜住，但速度会掉。
**先小批量试**：`python scripts/02_run_notes.py --only 1,2,3 --par 8` 跑通再加。

## 五、每层的上下文预算

| 层 | 每个任务要吞的输入 | token 估算 | 输出 |
|---|---|---|---|
| 一层（读原文） | 1 片 = 平均 5.2 万字，最大 6 万字 | ≈31k–60k | 摘要 1.5–3k 字 |
| 二层（读摘要） | 单卷几份摘要 = 6–9k 字 | ≈4k–6k | 卷纪要 3–5k 字 |
| meta（读书纪要） | 压缩材料 ≤6 万字 | ≈30k–40k | 800–4000 字 |

**二层的任务不要改读原文**：单卷原文 7–13 万字 ≈45k–132k token，偏长、变慢、还更贵，
读一层摘要就够。

## 六、防止并行跑歪的四条规则

1. **一个任务只读它自己那份输入。** 别让子代理"参考一下别的内容"——
   一个任务一旦看到别的片，摘要就开始串味。
2. **输出文件名必须唯一且可预测**（`notes/chunk_NN.md`）。
   两个任务写同一个文件 = 结果随机丢失。
3. **摘要模板先定死再开跑。** 几十个任务的格式不一致，后面没法机械合并，
   只能人工收拾——并行省下的时间全赔进去。
4. **不许子代理之间"商量"。** 需要跨片信息的地方（时间线、伏笔、角色状态），
   交给二层的卷纪要任务去做，那是有意设计的合并环节。

## 七、失败与重跑

```bash
python scripts/02_run_notes.py                # 重跑：已完成自动跳过，只补缺的
python scripts/02_run_notes.py --only 07,23   # 指定补
python scripts/03_merge_notes.py --check      # 覆盖率校验，缺片直接列出来
```

判断"跑完了"不能只看退出码：

- `03_merge_notes.py` 会做**片尾覆盖检查**（取每片最后几行的特征词回查摘要），
  模型跳读时不会报错，只会给你一份缺中段的摘要。
- 抽查几份摘要，确认「原文文风样本」是逐字原文而不是模型改写过的句子。
